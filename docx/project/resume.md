技术栈：Spring Boot、MyBatis、MySQL、Redis、Redisson、RabbitMQ、JWT、Vue3、Python、Ollama/百炼、Chroma、OSS。

项目周期按自己的实际投入日期填写；角色可写“个人开发”，不要虚构团队人数、企业任职或真实机构上线。

## 可直接改写的简历版本

围绕图书馆读者、馆员和管理员场景，完成馆藏、借阅/续借/归还、资格审批、政策确认、阅读计划、消息和AI辅助办理的一体化系统，采用Java业务后端、Vue界面及Python智能体服务。

- 设计成员类型与角色授权分离的模型，基于roleId、permission.code和数据范围统一校验，结合JWT/Redis会话撤销及最新须知限制，保护个人与管理侧聚合查询及敏感写入。
- 实现借阅审批与归还事务，通过Redisson资源读写锁、数据库行锁、乐观锁及状态条件协调副本库存、申请状态和成员额度，处理重复提交、并发审批、重复归还及续借次数限制。
- 实现数据库消息与事务Outbox，结合RabbitMQ职责队列、独立ACK、幂等消费和WebSocket提醒，支持离线补查，并处理已读与积压索引任务之间的竞态。
- 将咨询与业务智能体接入原有业务接口，采用RAG与只读工具区分文档知识和实时数据，业务写操作先生成提案并经用户确认，模型失败时降级本地或规则路径。
- 编写JUnit/MockMvc、前端组件及Python测试，并开展专项真实HTTP联调，覆盖角色越权、状态流转、版本冲突、缓存与消息一致性等边界。

简历篇幅有限时保留前三条或选择与岗位最相关的三条。不要把所有技术名称都堆进同一句，也不要给未测量的性能填写百分比。

## 30秒介绍

“我做了一个带AI助手的图书馆管理项目。业务核心仍在Java里，包含借阅审批、续借、归还、资格和额度控制。重点处理了多记录更新、角色和数据范围、消息可靠投递等问题。AI部分负责咨询与生成可确认的业务提案，实际执行仍复用Java权限和事务，不让模型决定用户有没有权限。”

## 建议展示的三条业务链

1. 分类/书目/副本建档 → 读者申请 → 馆员批准 → 续借 → 归还，检查库存和未归还数量。
2. 向离线用户发消息 → 上线补查 → 标记已读 → 重复消费索引任务不会重新变未读。
3. 咨询检索知识来源 → 业务AI提出申请草稿 → 用户取消时无写入 → 确认后返回原业务执行结果。

## 面试追问准备

| 问题 | 应解释的真实实现 |
| --- | --- |
| 为什么不只用乐观锁？ | 多行聚合状态与重复创建场景不能只靠单行version；资源锁、事务和唯一约束各自覆盖不同问题 |
| Redis锁能替代数据库事务吗？ | 不能；事务保证数据库内原子性，锁协调受控入口，仍需状态/版本和必要行锁 |
| 缓存是否强一致？ | 不是跨库原子事务；解释同资源键读写锁、删除重试及剩余故障边界，不夸大保证 |
| 为什么有Outbox？ | 避免业务提交后丢失发布意图；Broker确认后再标记，重复发布由消费者幂等处理 |
| 为什么两个消费者不放同一个工作队列？ | 同队列竞争消费不能保证两种职责都执行；需要职责队列各自收到事件与独立ACK |
| 消息已读后积压任务来了怎么办？ | Redis标记只是加速，索引写入需要数据库收件关系复核和协调，不能只信旧事件 |
| AI写操作怎么防越权？ | Skill白名单、可信用户、Java二次权限/范围/状态校验、提案确认及requestHash |
| 为什么不把所有表放进向量库？ | 库存、额度、权限属于实时结构化事实，工具读取更准确；RAG适合版本化文档知识 |
| 推荐算法是什么？ | 规则候选与兴趣/反馈评分，AI只在候选内重排；不是训练出来的深度推荐系统 |
| 你实际测试了什么？ | 打开测试类和可复现命令，区分H2/模拟依赖、真实HTTP和真实云端联调 |

## 可以与不可以写的数字

- 可以引用有日志的测试结果，但注明日期和范围，例如“本地业务回归364项Java测试通过”。新增测试后应更新数字。
- 接口索引中的127是HTTP方法＋路径注册项，包含别名，不应称作127种独立业务能力。
- 不写未经压测的QPS、延迟下降、缓存命中率、百万用户、生产零故障或商业收益。
- 不把AI生成代码辅助开发隐瞒为企业团队交付。准备好解释关键代码、取舍和问题修复，项目价值来自能复现并讲清实现。
